# H0.1 — Formato de errores común

> Referencia de diseño para [issue #2](https://github.com/Andr3sCid/Hevyfit/issues/2) del milestone H0. Fundaciones.
> Estado: diseño cerrado, pendiente de pasar a plan de implementación.

## Contrato JSON

Toda respuesta de error 4xx/5xx de ambas APIs (`hevyfit-api-measurements`, `hevyfit-api-routines`) sigue este esquema, plano (sin envoltorio `"error"`):

```json
{
  "code": "VALIDATION_ERROR",
  "message": "Datos inválidos",
  "details": [
    { "field": "height", "code": "FIELD_REQUIRED" }
  ]
}
```

- `code`: clave i18n estable (no texto libre), identifica el tipo de error.
- `message`: mensaje humano. Ver sección "Resolución de idioma del mensaje" más abajo.
- `details`: opcional, lista de errores por campo — solo aplica a validación con múltiples campos inválidos. Se omite o va vacía en errores sin detalle (ej. 404, 500).

Se descartó envolver la respuesta en `{ "error": {...} } ` por simplicidad: ni web ni mobile necesitan hoy metadata hermana (ej. `requestId`); si hiciera falta trazabilidad se resuelve con un header (`X-Request-Id`), no en el body.

## Jerarquía de excepciones y códigos HTTP

Vive en `hevyfit-common`, paquete `com.hevyfit.common.error`. Ambas APIs la reutilizan lanzando estas excepciones desde su código de negocio, sin tocar JAX-RS directamente.

- `ErrorCode` — enum con los códigos estables. Set inicial: `VALIDATION_ERROR`, `NOT_FOUND`, `UNAUTHORIZED`, `FORBIDDEN`, `INTERNAL_ERROR`, más códigos de campo (`FIELD_REQUIRED`, `FIELD_INVALID`, `FIELD_TOO_LONG`, `FIELD_TOO_SHORT`, `FIELD_OUT_OF_RANGE`), extensible según haga falta.
- `ErrorResponse` (record) — `code`, `message`, `details`.
- `ErrorDetail` (record) — `field`, `code`.
- `HevyFitException` — clase abstracta (`RuntimeException`), con `errorCode()`, `details()` y `httpStatus()` (cada subclase fija su propio status HTTP; el mapper no adivina con `instanceof`).

| Excepción | HTTP | `code` |
|---|---|---|
| `ValidationException` | 400 | `VALIDATION_ERROR` |
| `UnauthorizedException` | 401 | `UNAUTHORIZED` |
| `ForbiddenException` | 403 | `FORBIDDEN` |
| `NotFoundException` | 404 | `NOT_FOUND` |
| *(fallback genérico, sin excepción propia)* | 500 | `INTERNAL_ERROR` |

El 500 no tiene excepción propia: es el catch-all para cualquier fallo no anticipado (bug, infraestructura). Un mapper aparte para `Throwable` no expone el mensaje real (evita filtrar detalles internos), usa el mensaje genérico de `INTERNAL_ERROR` y loguea el stacktrace completo del lado del servidor.

`UnauthorizedException`/`ForbiddenException` quedan listas para que H1 (auth) las use en cuanto exista el middleware de JWT; no se ejercitan todavía porque no hay auth implementada.

## Resolución de idioma del mensaje

`hevyfit-common` resuelve `message` leyendo el header `Accept-Language` de cada request contra un bundle mínimo (`ResourceBundle` estándar de Java, arrancando solo con `es`; sin match, cae a `es`). No depende de usuario logueado ni de H1/H0.3 completos — cuando se construya H0.3, solo agrega más archivos de idioma al mismo bundle, sin tocar el mecanismo.

## Cobertura de mappers

Además de la jerarquía propia, se cubren los errores que genera el framework, para que **ningún** 4xx/5xx escape del esquema común:

| Mapper | Qué captura | Cuándo dispara |
|---|---|---|
| `HevyFitExceptionMapper` | `HevyFitException` (y toda subclase) | El código de negocio lanza `ValidationException`, `NotFoundException`, etc. a propósito |
| `ConstraintViolationExceptionMapper` | `ConstraintViolationException` (Hibernate Validator) | Falla la validación automática de un `@Valid` en el body/params de un endpoint, antes de llegar al código de negocio — cada violación se traduce a un `ErrorDetail {field, code}` |
| `JaxRsExceptionMapper` | `WebApplicationException` (JAX-RS) | Casos que genera el propio framework, ej. una ruta que no matchea (404 nativo) o un método no permitido (405) — traduce por status HTTP al `ErrorCode` más cercano. (Nombre elegido a propósito sin "Web": es backend puro, cubre por igual a los clientes web y mobile — "Web" en `WebApplicationException` es el nombre estándar de JAX-RS, no tiene relación con el frontend web) |
| `FallbackExceptionMapper` | `Throwable` (catch-all) | Cualquier error no anticipado → 500 `INTERNAL_ERROR`, sin exponer el mensaje real; se loguea el stacktrace completo del lado del servidor |

## Dependencias y registro en Quarkus

**Dependencias nuevas en `hevyfit-common`** (hoy es un jar Java puro, sin dependencias de framework):

- `jakarta.ws.rs:jakarta.ws.rs-api` — scope `provided`
- `jakarta.validation:jakarta.validation-api` — scope `provided`

`provided` porque son solo las interfaces estándar de Jakarta EE (no una implementación concreta): alcanza para compilar, y en runtime cada API aporta su propia implementación real vía Quarkus (RESTEasy Reactive + Hibernate Validator). Se prefieren sobre depender directo de `quarkus-rest`/artefactos de Quarkus porque el código no usa nada específico de Quarkus (todo es JAX-RS/Bean Validation estándar), y `hevyfit-common` no importa el `quarkus-bom` — traer artefactos de Quarkus sin ese BOM obligaría a fijar versiones a mano, con riesgo de desalinearse con la versión que usa cada API (`3.39.4`).

**Registro automático en cada API:** los mappers son clases `@Provider` dentro de un jar externo (`hevyfit-common`). Para que Quarkus los descubra sin registro manual, cada API agrega a su `application.properties`:

```properties
quarkus.index-dependency.hevyfit-common.group-id=com.hevyfit
quarkus.index-dependency.hevyfit-common.artifact-id=hevyfit-common
```

Esto indexa el jar externo vía Jandex en build time y trata sus `@Provider`/beans CDI igual que si fueran del propio proyecto.

## Testing

**Pruebas unitarias en `hevyfit-common`:** cada mapper separa la lógica pura (excepción → `ErrorResponse`) del envoltorio JAX-RS — ej. `HevyFitExceptionMapper.toResponse(ex)` llama a un método `toErrorResponse(ex)` y recién ahí arma el `Response`. La parte pura no necesita servidor levantado ni implementación de JAX-RS (son objetos Java normales), así que se testea con JUnit directo en el módulo, sin `@QuarkusTest`. Cubre:

- Resolución de idioma: distintos `Accept-Language` (match exacto, sin match → cae a `es`, header ausente → `es`).
- `FallbackExceptionMapper`: nunca expone `ex.getMessage()`, siempre usa el mensaje genérico de `INTERNAL_ERROR`.
- `JaxRsExceptionMapper`: traduce cada status HTTP relevante al `ErrorCode` correcto.
- `ConstraintViolationExceptionMapper`: cada tipo de constraint (`@NotNull`, `@Size`, etc.) mapea al `ErrorCode` de campo esperado. Para esto se agrega `hibernate-validator` como dependencia de **test** en `hevyfit-common` (scope `test`, no afecta a quien consume la librería) — permite validar un bean de prueba chico y obtener `ConstraintViolation` reales en vez de simularlos a mano.

**Pruebas de integración por API:** ninguna de las dos APIs tiene todavía endpoints de negocio reales (son hello-world). Se agrega una clase de recurso **solo de test** por API (ej. `ErrorFormatTestResource` en `src/test/java`, nunca llega a producción) con dos endpoints que fuerzan cada caso: uno lanza `ValidationException`, el otro `NotFoundException`. Un test (`ErrorFormatTest`, con RestAssured vía `@QuarkusTest`) golpea esos dos endpoints y verifica status HTTP, `code` esperado, y que `details` tenga la forma `{field, code}` en el caso de validación — queda como comprobación liviana de que el HTTP real responde bien, no donde vive el peso de la lógica (eso ya está cubierto por las pruebas unitarias de arriba). Se repite igual en ambas APIs (mismo mecanismo, distinto módulo), cumpliendo el criterio de aceptación "test por API que verifique el formato en un caso de validación y uno de 'no encontrado'".
